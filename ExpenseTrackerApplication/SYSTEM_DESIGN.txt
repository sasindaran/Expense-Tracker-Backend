                           1. SYSTEM OVERVIEW
================================================================================

Purpose:
  The Expense Tracker is a backend application designed to help users manage
  their personal expenses. It provides RESTful APIs for creating, retrieving,
  and deleting expense records with secure user authentication.

Key Features:
  - User authentication and authorization
  - Role-based access control (USER, ADMIN)
  - Expense CRUD operations
  - Category-based expense organization
  - User-specific data isolation
  - Secure password encryption

Target Users:
  - Individual users tracking personal expenses
  - Administrators managing the system

Business Goals:
  - Provide secure expense tracking
  - Ensure data privacy and isolation
  - Enable easy expense categorization
  - Support future analytics and reporting

│                                                                  │

│   - UNIQUE INDEX (name)                                          │

┌─────────────────────────────────────────────────────────────────┐
│                        EXPENSES TABLE                            │
├─────────────────────────────────────────────────────────────────┤
│ PK  id              BIGINT AUTO_INCREMENT                        │
│ FK  user_id         BIGINT NOT NULL → users.id                   │
│ FK  category_id     BIGINT NOT NULL → categories.id              │
│     amount          DECIMAL(10,2) NOT NULL                       │
│     description     VARCHAR(255)                                 │
│     expense_date    DATE NOT NULL                                │
│     created_at      DATETIME                                     │
│                                                                  │
│ Indexes:                                                         │
│   - PRIMARY KEY (id)                                             │
│   - FOREIGN KEY (user_id) REFERENCES users(id)                   │
│   - FOREIGN KEY (category_id) REFERENCES categories(id)          │
│   - INDEX (user_id) for faster user-based queries                │
│   - INDEX (expense_date) for date-range queries                  │
└─────────────────────────────────────────────────────────────────┘

Entity Relationships:

  roles (1) ──────< (N) users
                         │
                         │ (1)
                         │
                         ↓
                      (N) expenses (N) >────── (1) categories

Relationship Details:
  - One Role can have Many Users (1:N)
  - One User can have Many Expenses (1:N)
  - One Category can be used in Many Expenses (1:N)
  - Each Expense belongs to exactly One User (N:1)
  - Each Expense belongs to exactly One Category (N:1)

Data Integrity Constraints:
  ✓ Primary Keys: Auto-increment for all tables
  ✓ Foreign Keys: Enforce referential integrity
  ✓ Unique Constraints: email, role name, category name
  ✓ Not Null Constraints: Essential fields
  ✓ Cascading: Consider ON DELETE behavior

                        6. SECURITY ARCHITECTURE
================================================================================

Authentication Flow:

┌─────────────────────────────────────────────────────────────────┐
│ 1. User sends credentials (email + password)                     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 2. Spring Security intercepts request                            │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 3. CustomUserDetailsService.loadUserByUsername() called          │
│    - Queries database for user by email                          │
│    - Retrieves user with role                                    │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 4. Password verification                                         │
│    - BCryptPasswordEncoder compares passwords                    │
│    - Hashed password from DB vs. provided password               │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 5. Authentication object created                                 │
│    - Contains user details and authorities (roles)               │
│    - Stored in SecurityContext                                   │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 6. Request proceeds to controller                                │
│    - Authentication object available via method parameter        │
│    - User email extracted: authentication.getName()              │
└─────────────────────────────────────────────────────────────────┘

Authorization Flow:

┌─────────────────────────────────────────────────────────────────┐
│ Request to /expenses/**                                          │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ Spring Security checks SecurityFilterChain rules                 │
│ - Requires USER role                                             │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ Checks authenticated user's roles                                │
│ - If USER role present → Allow                                   │
│ - If not → 403 Forbidden                                         │
└─────────────────────────────────────────────────────────────────┘

Security Features:

  ┌────────────────────────────────────────────────────────────┐

================================================================================
                             7. API DESIGN
================================================================================

RESTful Principles:

  ✓ Resource-based URLs (/expenses)
  ✓ HTTP methods for operations (GET, POST, DELETE)
  ✓ Stateless communication
  ✓ JSON request/response format
  ✓ Proper HTTP status codes

API Endpoints:

┌─────────────────────────────────────────────────────────────────┐
│ POST /expenses                                                   │
├─────────────────────────────────────────────────────────────────┤
│ Purpose: Create new expense                                      │
│ Request: JSON body with expense details                          │
│ Response: Created expense with ID (200 OK)                       │
│ Authentication: Required (USER role)                             │
│ Idempotency: No (creates new resource each time)                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ GET /expenses                                                    │
├─────────────────────────────────────────────────────────────────┤
│ Purpose: Retrieve all expenses for authenticated user            │
│ Request: No body required                                        │
│ Response: Array of expense objects (200 OK)                      │
│ Authentication: Required (USER role)                             │
│ Idempotency: Yes (safe operation)                                │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ DELETE /expenses/{id}                                            │
├─────────────────────────────────────────────────────────────────┤
│ Purpose: Delete specific expense                                 │
│ Request: ID in URL path                                          │
│ Response: No content (200 OK)                                    │
│ Authentication: Required (USER role)                             │
│ Idempotency: Yes (multiple deletes have same effect)             │
│ Validation: Ensures user owns the expense                        │
└─────────────────────────────────────────────────────────────────┘

Response Formats:

  Success Response (Expense Object):
  {
    "id": 1,
    "user": { "id": 1, "email": "user@example.com", ... },
    "category": { "id": 1, "name": "Groceries", ... },
    "amount": 150.50,
    "description": "Grocery shopping",
    "expenseDate": "2026-01-20",
    "createdAt": "2026-01-20T14:38:00"
  }

  Error Response:
  {
    "timestamp": "2026-01-20T14:38:00",
    "status": 400,
    "error": "Bad Request",
    "message": "Validation failed"
  }

HTTP Status Codes:

  200 OK - Successful request
  400 Bad Request - Invalid input
  401 Unauthorized - Authentication failed
  403 Forbidden - Insufficient permissions
  404 Not Found - Resource not found
  500 Internal Server Error - Server error

================================================================================
                         10. DESIGN PATTERNS
================================================================================

Patterns Used in the Application:

┌─────────────────────────────────────────────────────────────────┐
│ 1. Layered Architecture Pattern                                 │
├─────────────────────────────────────────────────────────────────┤
│ Separates concerns into distinct layers:                        │
│ - Presentation (Controllers)                                     │
│ - Business Logic (Services)                                      │
│ - Data Access (Repositories)                                     │
│ - Domain Model (Entities)                                        │
│                                                                  │
│ Benefits:                                                        │
│ ✓ Clear separation of concerns                                  │
│ ✓ Easy to test each layer independently                          │
│ ✓ Maintainable and scalable                                      │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 2. Repository Pattern                                            │
├─────────────────────────────────────────────────────────────────┤
│ Abstracts data access logic:                                     │
│ - JpaRepository provides CRUD operations                         │
│ - Custom query methods defined by naming convention              │
│ - Hides database implementation details                          │
│                                                                  │
│ Benefits:                                                        │
│ ✓ Decouples business logic from data access                      │
│ ✓ Easy to switch databases                                       │
│ ✓ Testable with mock repositories                                │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 3. Dependency Injection Pattern                                  │
├─────────────────────────────────────────────────────────────────┤
│ Spring manages object creation and dependencies:                 │
│ - Constructor injection for required dependencies                │
│ - Loose coupling between components                              │
│ - Inversion of Control (IoC)                                     │
│                                                                  │
│ Benefits:                                                        │
│ ✓ Loose coupling                                                 │
│ ✓ Easy to test with mocks                                        │
│ ✓ Centralized configuration                                      │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 4. Data Transfer Object (DTO) Pattern (Implicit)                │
├─────────────────────────────────────────────────────────────────┤
│ Entities serve as DTOs in API responses:                         │
│ - Expense, User, Category objects transferred as JSON            │
│ - Jackson automatically serializes/deserializes                  │
│                                                                  │
│ Note: For production, consider separate DTO classes to:          │
│ - Hide sensitive fields (e.g., password)                         │
│ - Prevent over-fetching                                          │
│ - Version API contracts                                          │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 5. Service Layer Pattern                                         │
├─────────────────────────────────────────────────────────────────┤
│ Business logic encapsulated in service classes:                  │
│ - ExpenseService handles expense operations                      │
│ - UserService handles user operations                            │
│ - Reusable across multiple controllers                           │
│                                                                  │
│ Benefits:                                                        │
│ ✓ Centralized business logic                                     │
│ ✓ Reusable across different interfaces                           │
│ ✓ Transaction management                                         │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 6. Builder Pattern (via Lombok)                                 │
├─────────────────────────────────────────────────────────────────┤
│ Lombok annotations generate builders:                            │
│ - @NoArgsConstructor, @AllArgsConstructor                        │
│ - Simplifies object creation                                     │
│                                                                  │
│ Benefits:                                                        │
│ ✓ Reduces boilerplate code                                       │
│ ✓ Immutable object creation                                      │
└─────────────────────────────────────────────────────────────────┘
